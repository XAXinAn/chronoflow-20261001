## 1. 项目概述

### 1.1 项目背景与意义

日程管理与待办清单是现代人日常使用频率最高的效率工具之一。现有产品普遍存在两个断层：

- **个人与组织割裂**：个人日程工具很少能承接学校、企业等组织的统一通知下发，组织侧的通知又往往停留在即时聊天与纸质通知，成员需要反复手工转抄到自己的日历；
- **录入成本高**：新增一条日程需要逐项填写标题、日期、时间、地点、提醒等字段，从一张通知截图到日历里的一条日程，人工转录动辄需要半分钟以上。

时纪流围绕这两个断层设计：在同一个账号体系内同时承载**个人日程**与**组织下发的日程**，并用**端侧图像识别 + 智能助手**把「录入」这一步的成本降到最低。

### 1.2 作品定位与目标用户

时纪流是一款智能日程与待办管理应用，服务三类使用者：

| 使用者 | 使用方式 | 核心诉求 |
| --- | --- | --- |
| 个人用户 | 手机 App（自助注册） | 管理自己的日历、日程、待办与提醒 |
| 组织成员 | 手机 App（组织账号认领） | 接收组织统一下发的日程，成员只读 |
| 组织管理员 / 平台运营方 | Web 后台 | 管理成员与部门、下发组织日程、平台运营与审计 |

### 1.3 主要功能

| 模块 | 主要功能 |
| --- | --- |
| 账号与登录 | 手机号验证码/密码登录；个人身份与多个组织身份隔离并存，登录后可无感切换 |
| 个人日历 | 月视图、节假日与调休标记、搜索、日程与待办双模型 |
| 日程与待办 | 单时间点日程、重复规则（RRULE）与单次例外、提醒、地点与地图、图片附件、日程与待办互转 |
| 组织日历 | 管理员按全员/部门/成员范围下发，成员只读接收；部门树与分级权限 |
| 智能助手「小安」 | 自然语言查询与创建个人日程、语音输入、写操作逐条授权 |
| 图片识别日程 | 端侧 OCR 识别通知截图，服务端解析成日程草稿，确认后一键添加 |
| Web 后台 | 平台超管端（组织、账号、配置、看板、审计）与组织管理端（成员、部门、组织日历、日志） |
| 应用内更新 | 启动静默检查版本，应用内下载校验并调用系统安装器升级 |

## 2. 设计目标与原则

| 目标 | 实现原则 |
| --- | --- |
| **数据隔离不依赖前端** | 越权校验强制在服务层实施，前端隐藏入口不作为安全边界 |
| **敏感信息最小化** | 图像在手机本地完成识别，仅上传识别出的文字；身份证号加密存储；客户端不持有任何第三方密钥 |
| **外部依赖可降级** | 地图、短信、推送、邮件、大模型、实名认证均为可插拔模块，未配置时如实提示「不可用」，不静默失败 |
| **接口契约唯一** | 全系统共用一份机器可校验的 API 契约，任何改动都必须同时满足契约门禁 |
| **可测试性优先** | 核心业务逻辑与界面、原生模块解耦，可在无设备环境下自动化测试 |

**首版范围之外**：组织日程暂不支持重复规则；智能助手暂不操作组织日程；iOS 端具备完整代码但出包需要 macOS 环境。

## 3. 系统总体设计

### 3.1 总体架构

系统采用「**一套服务端 + 两个客户端 + 一份接口契约**」的总体结构。客户端与第三方服务的所有交互都经过服务端，客户端不直接持有任何厂商密钥。

**表 1　系统组成**

| 层次 | 组成部分 | 技术栈 |
| --- | --- | --- |
| 客户端 | 手机 App | React Native + Expo（新架构） |
| 客户端 | Web 管理后台 | React + Vite + Ant Design |
| 接口契约 | API 契约 | 机器可校验的 JSON 契约（120 个端点），服务端与两个客户端共同遵守 |
| 服务端 | 后端服务 | Java 21 + Spring Boot 3 |
| 数据层 | 关系数据库 | PostgreSQL 16 |
| 数据层 | 缓存与验证码 | Redis 7 |
| 数据层 | 文件存储 | 可替换的本地存储实现（保留对象存储演进接口） |
| 外部服务 | 短信、推送、地图、邮件、实名认证、大模型 | 均为服务端代理的可插拔实现 |

**图 1　系统总体架构（数据流）**

| 序号 | 流向 | 说明 |
| --- | --- | --- |
| ① | App / Web → Nginx | 客户端统一经反向代理访问，HTTPS 终止 |
| ② | Nginx → 后端服务 | 按 `/api` 前缀转发到后端；静态资源与下载包由 Nginx 直接托管 |
| ③ | 后端 → PostgreSQL | 业务数据持久化，数据库结构由迁移脚本独占管理 |
| ④ | 后端 → Redis | 验证码、刷新令牌、限流计数等短时效数据 |
| ⑤ | 后端 → 第三方服务 | 短信、推送、地图、邮件、实名认证、大模型，全部由服务端发起 |

> 客户端与后端之间、后端与第三方之间均为单向调用，第三方不可用时通过降级实现保证核心功能可用（详见 §2 设计原则）。

### 3.2 服务端模块划分

服务端基于 **Java 21 与 Spring Boot 3** 实现，采用**模块化单体**架构：按业务域划分模块，模块之间只允许通过对方暴露的服务接口调用，不允许跨模块直接访问数据表。这样既保持了单体在部署和事务上的一致性优势，又保留了清晰的域边界。数据库结构由 Flyway 迁移脚本独占管理，应用启动时自动执行，保证代码与库结构始终一致。

**表 2　服务端模块**

| 模块 | 职责 |
| --- | --- |
| 公共模块 | 统一响应体、错误码、分页、业务异常、链路追踪 |
| 认证模块 | 短信/密码登录、身份列表与选择、令牌签发与刷新、身份创建 |
| 个人模块 | 个人日历、日程（重复规则与例外）、待办、提醒、节假日 |
| 组织模块 | 组织、部门树、成员管理、组织日程下发 |
| 智能助手模块 | 对话、工具调用循环、写操作授权、语音转写、图像文本解析 |
| 后台管理模块 | 组织、账号、管理员、全局配置、数据看板、审计日志 |
| 支撑模块 | 意见反馈、推送设备登记与消息推送 |
| 启动模块 | 应用装配、安全配置、全局异常、接口文档、数据库迁移 |

### 3.3 契约先行的接口设计

项目采用「契约先行」的接口设计：以一份机器可校验的 JSON 契约（120 个端点）作为服务端与两个客户端的共同约定，接口路径、鉴权方式与响应结构概以它为准。

- 后端必须以统一的分层结构覆盖契约中的全部端点（详见 §3.2），并提供与之对应的接口文档；
- 契约测试不仅校验接口文档的覆盖情况，还会实际发起不带令牌的请求，验证受保护接口的行为与声明一致（详见 §6.3）。

其工程价值在于：接口契约不再是「文档」，而是**可执行的验收标准**。任何一端偏离契约都会导致持续集成失败，从根本上避免了多端接口漂移。

## 4. 数据模型设计

### 4.1 核心实体

**表 3　核心数据实体**

| 实体 | 说明 |
| --- | --- |
| 账号 Account | 以手机号为唯一凭证的「人」的根实体 |
| 身份 Identity | 账号在某个空间下的操作主体，分为个人身份与组织身份 |
| 组织 Organization | 租户实体 |
| 部门 Department | 组织内的树形结构，最多 5 层 |
| 组织成员 OrgMember | 成员在组织内的档案，成员标识组织内唯一 |
| 日历 Calendar | 分为个人日历与组织日历 |
| 日程 Event | **只有一个时间点**的日历事件 |
| 待办 Task | 带完成状态的任务，可关联日程 |
| 下发 Dispatch / 收件 Recipient | 组织日程的投递关系与接收快照 |
| 提醒 Reminder | 挂在日程或待办上的提醒 |

### 4.2 关键设计决策

#### 4.2.1 账号与身份分离

系统把「人」和「人在某个空间下的操作主体」拆成两层：账号是以手机号为唯一凭证的根实体；身份是账号在某个空间下的主体，分为个人身份（每人一个）与组织身份（每组织一个）。

**设计收益**：一个账号可同时持有个人身份与多个组织身份，各身份的数据完全隔离，权限按当前激活身份判定。组织身份的生命周期独立——解绑即停用，不影响个人数据；鉴权所需的身份信息全部从令牌解析，服务端不信任请求体中的身份字段。

个人账号与组织账号是两套独立凭据：个人账号用手机号登录；组织账号以「组织编码 + 成员标识（学号/工号）」认领，成员首次登录时创建对应身份，且同一组织账号不能同时绑定到多个个人账号。

#### 4.2.2 部门树使用物化路径

部门树采用物化路径（形如 `/5/12/`）表达层级关系，使「本部门及所有下级部门」的查询退化为一次路径前缀匹配。路径以斜杠结尾，可避免 `/5` 误匹配 `/51` 的前缀问题。权限判定规则统一为：普通管理者的有效管理范围 = 其被授权部门的路径前缀匹配结果。

#### 4.2.3 日程使用单时间点模型

产品定义中，日程是「到点办事」的事件，不占用时间段，因此模型中没有起止时间与时长，只有 **`at` 一个必填时刻**。这一简化显著降低了重复规则展开、冲突判断与列表渲染的复杂度，也使「仅知道日期」的输入有明确语义（取当地 00:00）。

重复日程用标准 RRULE 表示，单次改动写入「例外」表。修改重复日程时支持三种生效范围：

| 范围 | 行为 |
| --- | --- |
| 全部 | 修改整条序列 |
| 仅本次 | 只对该次出现写入例外 |
| 本次及以后 | 原序列截断到本次之前，从本次克隆新序列并套用新值 |

#### 4.2.4 组织下发采用快照模型

组织日程下发时，系统按下发范围**展开为成员级的接收快照**，而不是在下发规则上做动态计算。这样成员端「发给我的日程」是一次简单查询，个人日程与组织日程的合并展示也无需运行时权限推导。

该设计带来一个明确约束：**下发之后新加入的成员不会自动补收历史日程**，如需补投必须由管理员显式操作。这是有意的取舍——保证「发给谁」的语义稳定、可审计。

**表 4　组织权限与下发范围**

| 角色 | 可管理部门 | 可下发范围 |
| --- | --- | --- |
| 组织拥有者 / 组织管理员 | 全组织 | 全员 / 任意部门 / 任意成员 |
| 部门管理员 | 被授权部门及其所有下级 | 本范围 / 范围内成员 |
| 普通成员 | 无 | 无（只读接收） |

## 5. 安全与权限设计

### 5.1 双认证体系

**表 5　认证体系**

| 体系 | 主体 | 凭据 | 令牌作用域 |
| --- | --- | --- | --- |
| 用户端 | 个人账号 | 手机号 + 验证码 / 密码；组织账号走「组织编码 + 成员标识」认领 | 用户作用域 |
| 后台 | 管理员 | 用户名 + 密码 | 管理作用域 |

两个作用域完全隔离：管理员令牌不能访问用户端业务接口，反之亦然。创建组织时同步创建首位管理员，避免出现无人可登录的空组织。

### 5.2 会话保持

| 令牌 | 有效期 | 说明 |
| --- | --- | --- |
| 访问令牌 | 2 小时 | 携带身份上下文 |
| 刷新令牌 | 90 天，滑动续期 | 每次刷新换发新的 90 天令牌 |
| 注册 / 选择身份令牌 | 30 分钟 | 仅用于首次建号与选定身份 |

为让正常使用的用户不感知到重新登录，令牌轮换设有**并发宽限期**：多个并发刷新请求在宽限期内提交旧令牌时，返回同一个新令牌，而不是判定失效。这解决了移动端最常见的「莫名要求重新登录」问题。

### 5.3 越权防护

- 所有读写操作在服务层校验「当前身份对该资源的所有权 / 组织归属 / 部门范围」；
- 组织日程对成员严格只读，写接口按权限矩阵拒绝；
- 停用组织后，其成员访问组织接口一律拒绝；
- 封禁账号或停用身份时，同步吊销该账号的全部刷新令牌，线上会话无法续期。

### 5.4 敏感信息保护

**表 6　敏感信息处理**

| 数据 | 保护措施 |
| --- | --- |
| 登录密码 | 单向哈希存储（BCrypt，强度不低于 cost 10） |
| 身份证号 | AES-GCM 加密存储，另存指纹用于唯一性判定，明文不落库 |
| 验证码 | 短时效存储 + 发送频控 + 校验一次性 |
| 手机号 / 邮箱 | 后台列表默认脱敏显示 |
| 图像 | 在手机本地完成识别，仅上传识别文字 |
| 第三方密钥 | 全部保存在服务端，客户端不持有 |
| 审计与登录日志 | 仅追加，不可修改或删除 |

### 5.5 合规设计

合规文本（隐私政策、用户协议、儿童隐私声明、信息收集清单、第三方共享清单）只有一份事实来源，服务端渲染为静态页面，App 内以网页形式打开同一地址——因此「App 内展示内容与应用商店提交链接完全一致」在结构上成立。项目还提供自动化的合规门禁脚本，在持续集成中逐项检查并拦截缺失。

## 6. 接口与契约设计

### 6.1 通用约定

**表 7　接口通用约定**

| 项 | 约定 |
| --- | --- |
| 风格 | REST，统一前缀 `/api/v1` |
| 鉴权 | Bearer 令牌；身份上下文由服务端从令牌解析 |
| 时间格式 | ISO 8601 带时区，存储统一转为 UTC |
| 分页 | 统一 `page` / `pageSize`，返回总数与列表 |
| 幂等 | 创建类接口支持幂等键 |
| 文档 | 自动生成开放接口文档 |

**统一响应体**：

```json
{ "code": 0, "message": "ok", "data": {}, "traceId": "…" }
```

其中 `code` 表示业务结果，`0` 为成功；`traceId` 贯穿请求全链路，便于定位问题。**可预期的业务错误同样返回 HTTP 200，语义由 `code` 表达**，仅参数错误、未认证、无权限、系统异常分别使用 400 / 401 / 403 / 500。

**表 8　错误码分段**

| 段 | 含义 | 示例 |
| --- | --- | --- |
| `1xxxx` | 通用与参数校验 | 参数缺失、格式错误 |
| `2xxxx` | 认证与鉴权 | 未登录、令牌过期、无权限、验证码过频 |
| `3xxxx` | 个人日历 / 日程 / 待办 | 日程时间非法、重复规则非法 |
| `4xxxx` | 组织 / 部门 / 成员 | 部门层级超限、成员已存在 |
| `5xxxx` | 组织日历与下发 | 下发目标为空 |
| `6xxxx` | 后台管理 | 管理员登录失败、需要双因素 |
| `9xxxx` | 系统 | 内部错误、第三方服务不可用 |

### 6.2 接口规模

系统共定义 **120 个接口**，按业务域划分如下：

**表 9　接口分布**

| 业务域 | 数量 | 说明 |

| 平台超管后台 | 24 | 组织、账号、管理员、配置、看板、审计 |
| 组织管理端 | 23 | 成员、部门、组织日历、批量导入 |
| 当前身份设置 | 17 | 资料、安全、实名、邮箱、设备管理 |
| 认证 | 8 | 登录、身份选择与切换、令牌刷新、登出 |
| 个人日程 / 待办 | 14 | 日程与待办的增删改查、完成、互转 |

| 成员视角组织接口 | 5 | 组织上下文、部门树、组织日程与已读 |
| 系统 | 3 | 探活、元信息、客户端版本信息 |
| 其他 | 16 | 提醒、地图、组织账号、反馈、合规文本、身份、节假日、搜索、上传 |

### 6.3 契约测试

接口契约的自动化测试不仅校验「文档是否覆盖了契约」，还会**实际发起一次不带令牌的请求**，验证受保护接口确实返回未认证、公开接口确实不返回未认证。这是行为验证而非文档验证——注解写错同样会导致构建失败。

## 7. 关键技术实现

### 7.1 智能助手「小安」：可授权的写操作

智能助手支持用自然语言查询日程、创建与修改个人日程，以及长按语音输入。其核心难点不是「让模型会说话」，而是**让模型在拥有写能力的同时不失控**。项目采用三条硬边界：

**（1）写操作必须逐条授权。** 模型本身没有写权限。当模型决定创建或修改日程时，只产出一条「授权请求」，App 将输入区让位给一块确认面板（形如「创建日程 · 动员大会 · 9 月 29 日 13:00」+ 允许 / 拒绝）。服务端阻塞等待用户答复，用户允许后由服务端调用既有业务服务真正写入，并把结果作为工具结果回填给模型，同一轮对话继续；用户拒绝则回一条「用户已拒绝、未做任何修改」，对话同样继续。

**（2）工具集极小且严格隔离。** 助手只暴露五个工具，且全部只作用于**当前用户个人的日程**：查询列表、分段读取备注、创建、修改、删除。他人日程一律按「查不到」处理，组织下发的日程不在助手范围内。工具名称中的 `my_` 前缀即强调这一隔离沙盒语义。

**（3）调用与结果严格配对。** 一轮内的工具调用按声明顺序推进，读与写都在服务端执行；对话历史中「模型的工具调用」与「工具返回结果」始终成对出现（客户端回放与服务端发送前各修一遍：缺失结果补中断标记、孤立结果丢弃），模型因此不会重复申请同一个动作。

**表 10　助手能力与边界**

| 维度 | 设计 |
| --- | --- |
| 查询能力 | 个人日程查询、空档推断 |
| 写能力 | 创建 / 修改 / 删除个人日程（均需用户授权） |
| 语音输入 | 长按说话转文字，填入输入框但不自动发送 |
| 数据边界 | 只碰当前用户个人日程；组织日程与他人日程不可见 |
| 隐私 | 聊天记录不落库，仅存在于本次运行内存；语音转文字后音频立即丢弃 |
| 可观测 | 每次工具调用在对话中留一行中文摘要，点开是可读明细 |
| 成本控制 | 限制上下文轮数、限制单次输出长度、默认使用轻量模型，可一行配置切换 |

### 7.2 端侧图像识别：图片不出手机

「拍照/传图一键加日程」的链路为：**端侧识别 → 服务端解析 → 确认页 → 草稿编辑器 → 一键添加**。

其中图像识别完全在手机本地完成，**原始图片不上传**，仅上传识别出的文字。这一设计既降低了网络依赖，也显著降低了隐私风险，是与合规要求协同设计的成果。

**表 11　端侧识别流水线**

| 步骤 | 处理内容 |
| --- | --- |
| 1 | 图像预处理：缩放、补齐、归一化，得到模型输入张量 |
| 2 | 文本检测：定位图中所有文本行区域 |
| 3 | 检测后处理：二值化、连通域分析、区域外扩、按阅读顺序排序 |
| 4 | 方向分类：逐区域判断是否需要旋转 |
| 5 | 文本识别：逐区域识别字符序列 |
| 6 | 序列解码：将模型输出解码为文字，拼接成段落 |
| 7 | 上传文字，由服务端解析为结构化日程草稿 |

识别模型体积约 16 MB，采用跨平台的推理运行时，同一份代码同时支持 iOS 与 Android；模型按需加载并在用户打开选择面板时预热，避免拖慢冷启动。

### 7.3 组织领导力模型：物化路径 + 快照下发

组织模块的两个关键实现是**部门树的物化路径**（见 §4.2.2）与**下发的快照展开**（见 §4.2.4）。两者共同把「谁能管谁、这条日程发给了谁」这两个最容易出错的问题，转化为可预测、可审计的确定性查询。

成员批量导入采用**异步执行 + 逐行独立事务**：上传后立即返回批次号，逐行结果异步产出；每条记录独立提交，某一行失败只影响该行，不会导致整批作废。

### 7.4 应用内更新

客户端启动时静默检查一次版本，也支持手动检查。判定依据是服务端返回的版本序号**严格大于**本机版本序号；下载在应用内进行并校验文件大小与摘要，安装交由系统安装器由用户确认。若服务端未配置发布信息，客户端明确认为「不提供更新」，绝不编造版本号。

### 7.5 可测试性设计

为让核心逻辑可以在没有真机的环境下自动化测试，项目做了两项结构约束：

- 客户端把**纯业务逻辑与界面、原生模块分离**：登录表单判定、重复规则、提醒计算、时间展示、草稿转换等全部放在不依赖原生模块的纯逻辑层，可直接在 Node 环境运行单元测试；
- 图像识别流水线通过**接口注入**推理与读图能力，测试时以模拟实现端到端跑通，覆盖坐标偏移、顺序错乱、置信度偏低等异常场景。

服务端测试使用嵌入式数据库与嵌入式缓存，**不依赖容器即可运行**，并会真实执行全部数据库迁移脚本，保证迁移与代码始终一致。

## 9. 创新点总结

1. **个人与组织统一的身份模型**：通过账号与身份分离，一个账号同时承载个人与多个组织空间，各空间数据隔离、权限互不越界，解决了个人日程工具与组织通知割裂的问题。
2. **可授权的智能助手**：把「模型可以写」改造成「模型只能申请写、用户逐条授权」，并用调用与结果严格配对保证对话不重复申请动作，在可用性与可控性之间取得平衡。
3. **端侧识别 + 云端解析的两段式录入**：图像在手机本地完成识别、仅上传文字，既把录入成本降到「拍一张图」，又天然满足隐私最小化要求。
4. **契约先行的接口设计**：用一份可执行的接口契约约束服务端与两个客户端，把多端接口一致性从「靠人记」变成「机器守」。
5. **快照式组织下发**：以成员级接收快照换取稳定的投递语义与可审计性，配合物化路径实现高效的部门范围权限判定。

## 10. 应用价值与推广前景

- **对个人用户**：把「收到一张通知截图」到「日历里多一条日程」的操作从多次手工填写压缩为一次识别与确认，降低日程工具最大的使用门槛。
- **对学校与企业**：组织日历下发可替代逐级转发的通知方式，成员收到的日程直接进入个人日历，且下发范围与投递对象全程可审计。
- **对社会场景**：系统对节假日与调休做数据化维护，不把年度安排写死在代码里，换一年、改一次调休无需发版即可生效，适合长期运营。
- **技术推广**：端侧识别 + 服务端解析的两段式架构、契约先行的接口设计、可授权的智能助手交互模式，均可迁移到其他需要「拍照录入 + 智能辅助 + 组织分发」的管理类应用。
