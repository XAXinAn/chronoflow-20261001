## 二、待决策（按优先级）

### P0 —— 会直接影响上线

**R1. 提醒/通知/推送整条链路不存在（最严重的产品缺口）**

spec §4.1.2 承诺「每个日程/待办可配置多个提醒」、§4.5 承诺「服务端推送 + App 本地通知（极光）」，
实际：

- 后端只有存储层：`reminder` 表、`PUT/GET /reminders`、`identity.notification_prefs`、`PUT /me/notifications`；
  **没有任何投递机制**（全仓唯一的 `@Scheduled` 是节假日同步）；
- App **没有提醒 UI**（全局搜 `提醒|reminder` 只命中注销页文案），也没有 `expo-notifications` 依赖；
- 全仓搜不到 `jpush|PushProvider|push_token`。

后果：用户建了日程、期望到点提醒，**什么都不会发生**——这是日程类 App 的核心功能，
人工审核的「功能完整性」也容易卡。

建议（三选一，按性价比排序）：① 首版接 **本地通知**（`expo-notifications` 排期，服务端 `reminder` 已就绪，
不需要推送通道，成本最低）；② 接极光/厂商推送（要开发者账号）；③ 明确降级为「无提醒」，
同时改 spec §4.1.2/§4.5、隐私政策与商店的功能描述。

**R2. 明文 HTTP：release 包可能连不上后端**

`app/app.json` 的 `extra.apiBaseUrl` 是 `http://8.136.20.182:8088`；`app/node_modules` 里搜不到
`usesCleartextTraffic`（Expo 不注入该属性），而 Android 9+ 默认禁止明文流量。
**上线前必须在真实 release 包里确认**——最稳的做法是上域名 + HTTPS（隐私政策 URL 也要求 HTTPS）。
若只是内部演示包，用 `expo-build-properties` 打开 `android.usesCleartextTraffic`。

### P1 —— 功能/承诺不一致，需要拍板

**R3.「小安」tab 是空壳**
底部导航常驻，进去只会说「还没接入模型」（`AgentChatScreen.tsx`）。建议第一版先在导航里隐藏，
或与 R1 一起做掉。留着对「功能完整性」审核不利。

**R4. `login_log` 只记后台管理员登录，C 端登录从不记录**
`AdminAuthService.java:223` 是唯一写入点（`principal_type='ADMIN'`）；
表结构本身设计了 `ACCOUNT` + `account_id`/`identity_id`（`V2__account_and_identity.sql:53`）。
而**隐私政策明确声明**收集「登录日志（登录时间、登录结果、IP 地址）」并保留 ≥ 6 个月。
→ 要么补 C 端登录日志（推荐，顺带满足账号安全需求），要么把隐私政策改准。

**R5. spec §3.6 说「短信发送日志落库」，实际没有这张表也没有写入**
`spec.md` §3.6「存储」一行与 `db/migration` 全部 16 个文件对照即知。同 R4 的处理思路。

**R6. i18n 完全没做，但 spec §10.5-5 把它列为验收标准**
全仓搜不到 `i18n|useTranslation|intl`（spec §7.3 也承诺了国际化）。要么实现，要么从验收标准里去掉。

**R7. 15 个契约端点没有任何客户端调用**
多日历 CRUD（`/calendars/{id}` GET/PATCH/DELETE）、日程⇄待办互转、`/me/devices`、
`/me/notifications`、`/auth/login/password`、`PUT /me/password`、`/system/info|ping`、
`/ai/events/recognize`。要么补 UI，要么标注「保留供后续版本」。
其中「设密码」缺失使「手机号+密码登录」这条路永远走不通（两端都没有入口）。

**R8. 11 个 spec 写明但契约与实现都没有的端点**
`/auth/login/wechat`、`/me/bind/wechat|email|{channel}`、`/admin/auth/mfa/verify|logout|token/refresh`、
`/admin/login-logs`、`/org/events/{id}`、`/org/notifications`、`/events/{id}/exceptions`。
spec 需要标注阶段二或删除（§3.3 甚至把微信登录标了「首版 ✔」）。

## 四、产品决定（本轮确认，别再翻）

- **管理员模型保持现状**：组织管理员 / 拥有者在 **Web 组织管理端**设置部门管理员
  （`POST /org-admin/departments/{id}/managers`，服务端要求 `requireOrgAdmin`）；
  部门管理员可管「被授权部门及其所有下级」，但**不能**再往下授权。
  **App 端不提供成员/角色管理界面，也不设管理员数量上限。**
  （2026-09-27 产品确认：不做 App 端添加管理员、不做「一个组织最多 5 个管理员」的限制。）
