### 1.2 选型理由

**表 3　关键技术选型说明**

| 选择 | 理由 |
| --- | --- |
| Spring Boot 模块化单体 | 业务规模以万级用户量级为设计目标，单体在事务一致性、部署与排障上明显优于微服务；按业务域拆 Maven 模块后，域边界仍然清晰，将来需要拆分时切面是现成的 |
| MyBatis-Plus | 复杂查询（范围查询、物化路径前缀匹配、看板统计）需要精确控制 SQL，ORM 的自动生成反而不便；MyBatis-Plus 保留手写 SQL 的自由，同时提供分页与基础 CRUD 能力 |
| PostgreSQL | 需要 `jsonb`、部分唯一索引（如「每账号一个个人身份」）、`timestamptz` 精确时区语义与丰富索引类型，PostgreSQL 在同一套引擎里全部满足 |
| Redis | 验证码与刷新令牌是短时效、高频、可丢失的数据，放关系库既污染业务表又增加写压力；同时用它实现发送频控 |
| JWT（JJWT） | 无状态访问令牌，接口层无需查库即可解析身份上下文；配合服务端维护的刷新令牌索引实现可控的注销与踢设备 |
| lib-recur | 重复日程采用标准 RFC 5545 的 RRULE 表达，交给成熟库展开，避免自行实现历法规则带来的边界缺陷 |
| Flyway | 数据库结构变更必须可追溯、可重放。Flyway 以校验和保证历史脚本不可篡改，应用启动即自动升级 |

## 2. 工程结构与分层

### 2.1 模块划分

后端是一个多模块 Maven 工程，按业务域拆分，由启动模块统一装配：

**表 4　后端模块与职责**

| 模块 | 职责 | 对外依赖 |
| --- | --- | --- |
| 公共模块 `common` | 统一响应体、错误码、分页结构、业务异常、链路追踪过滤器 | 无 |
| 认证模块 `auth` | 短信/密码登录、身份选择与切换、令牌签发与刷新、身份创建 | 公共模块 |
| 个人模块 `personal` | 个人日历、日程、待办、提醒、节假日 | 公共模块 |
| 组织模块 `org` | 组织、部门树、成员、组织日程下发与查询 | 公共模块 |
| 智能助手模块 `agent` | 对话、工具循环、写操作授权、语音转写、图像文本解析 | 公共模块、个人模块 |
| 后台模块 `admin` | 组织、账号、管理员、全局配置、看板、审计 | 公共模块、组织模块 |
| 支撑模块 `support` | 意见反馈、推送设备与消息推送、图片上传 | 公共模块 |
| 启动模块 `bootstrap` | 应用装配、安全配置、全局异常、接口文档、系统接口、数据库迁移 | 全部模块 |

**模块依赖规则**：模块之间只允许通过对方暴露的服务接口调用，**禁止跨模块直接访问数据表**。这条规则保证域边界在单体内部依然成立。

### 2.2 分层约定

```
Web 层（Controller）      协议转换、参数校验、鉴权注解
    ↓
服务层（Service）         业务规则、事务边界、越权校验
    ↓
数据访问层（Mapper）        SQL 与结果映射
    ↓
PostgreSQL / Redis
```

三条约定：

1. **Controller 不写业务判断**，只做协议转换与参数校验；
2. **越权校验必须落在服务层**，不能依赖接口层注解或前端隐藏入口；
3. **数据访问层不做权限判断**，它的职责只有数据读写。

### 2.3 启动模块组成

**表 5　启动模块关键组件**

| 组件 | 职责 |
| --- | --- |
| 应用入口 | 启动 Spring Boot 应用 |

## 3. 数据库设计

### 3.1 版本管理

数据库结构由 **Flyway 独占管理**，迁移脚本位于启动模块的资源目录下，按 `V1`、`V2`…… 顺序编号，当前已迭代到 `V20`。

两条硬规则：

1. **只增不改**：历史脚本一个字节都不能改动。Flyway 以校验和识别变更，改动历史脚本会导致存量数据库直接启动失败；
2. **新改动新开脚本**：应用启动时自动执行未应用的迁移，因此「部署新版本」即等于「完成数据库升级」，无需手工连库操作。

### 3.2 核心表清单

**表 6　按业务域划分的核心表**

| 业务域 | 主要表 |
| --- | --- |
| 账号与认证 | 账号、身份、后台管理员、登录日志 |
| 组织与部门 | 组织、部门、组织成员、部门管理员 |
| 日历与日程 | 日历、日程、日程例外、待办、提醒 |
| 组织下发 | 下发记录、接收记录 |
| 导入与审计 | 导入批次、导入行结果、审计日志、系统配置 |
| 支撑域 | 意见反馈、推送设备、节假日 |

### 3.3 关键表设计

**表 7　账号与身份**

| 表 | 关键字段 | 约束与说明 |
| --- | --- | --- |
| 账号表 | 手机号、验证时间、密码哈希、微信标识、邮箱、状态、最后登录时间 | 手机号全局唯一；微信标识唯一且可空 |
| 身份表 | 账号、身份类型、组织、昵称、头像、时区、通知偏好、状态 | 部分唯一索引保证「每账号至多一个个人身份」「每账号每组织至多一个组织身份」；个人身份的组织字段必须为空 |

身份表的设计要点：组织身份在成员**首次登录组织账号**时创建，解绑时置为停用而**不物理删除**——唯一索引仍被占用，保留该行同时保留了绑定历史，避免「解绑后重新登录」产生唯一键冲突。

**表 8　组织与部门**

| 表 | 关键字段 | 约束与说明 |
| --- | --- | --- |
| 组织表 | 名称、组织编码、联系人、时区、状态、成员上限、到期时间 | 组织编码全局唯一；支持软删除 |
| 部门表 | 组织、父部门、名称、**物化路径**、层级、排序 | `(组织, 父部门, 名称)` 唯一；层级不超过 5；路径形如 `/1/5/12/` |
| 组织成员表 | 组织、身份、部门、成员标识、姓名、组织角色、状态 | `(组织, 成员标识)` 唯一且非空；`(组织, 身份)` 唯一；**不存密码** |
| 部门管理员表 | 部门、成员、授权人 | `(部门, 成员)` 唯一 |

物化路径是组织权限模型的基础：判断「本部门及其所有下级」只需一次路径前缀匹配。路径以斜杠结尾，可避免 `/5` 误匹配 `/51` 这类的经典前缀问题。

**表 9　日历、日程与待办**

| 表 | 关键字段 | 约束与说明 |
| --- | --- | --- |
| 日历表 | 类型、所属身份、所属组织、名称、颜色、时区 | 个人日历必填所属身份；组织日历必填所属组织 |
| 日程表 | 日历、组织、创建身份、来源、标题、**时间点**、时区、重复规则、状态、地点字段、优先级、分类 | **只有单一时间点，没有起止时间与时长**；地点拆为名称、地址、详细地址、经纬度、POI、坐标系 |
| 日程例外表 | 日程、出现日期、例外类型、覆盖时间 | `(日程, 出现日期)` 唯一 |
| 待办表 | 日历、所属身份、父待办、关联日程、标题、截止时间、状态、优先级、图片 | 仅支持父/子两层；删除关联日程时置空而非级联删除 |
| 提醒表 | 目标类型、目标、身份、出现日期、提前分钟数、渠道、启用 | 唯一约束覆盖「同一目标同一身份同一提前量」 |

日程采用单时间点模型是核心设计决策：产品定义为「到点办事」，去掉时间段后，重复规则展开、冲突判断与列表渲染都显著简化。重复日程本身只在一条记录上保存规则，单次改动写入例外表。

**表 10　组织下发**

| 表 | 关键字段 | 约束与说明 |
| --- | --- | --- |
| 下发表 | 日程、组织、范围类型、范围部门、是否含下级、发起成员、发起管理员、状态、接收人数 | 两个发起方字段**恰有一列非空**；撤回置为已撤销 |
| 接收表 | 下发、日程、成员、部门、已读时间 | `(下发, 成员, 出现日期)` 唯一；下发时按范围**快照展开** |

### 3.5 数据规范

- 时间列统一使用带时区的时间戳类型，写入前转换为 UTC；接口出入参携带时区；
- 逻辑删除统一使用删除时间字段，查询默认过滤；
- 所有业务表带创建时间与更新时间，由框架自动填充；
- JSON 结构（通知偏好、图片数组、审计明细）使用 `jsonb` 存储，并注册自定义类型处理器。

## 4. 接口技术规范

### 4.1 通用约定

**表 12　接口约定**

| 项 | 约定 |
| --- | --- |
| 风格 | REST，统一前缀 `/api/v1` |
| 传输 | HTTPS + JSON |
| 鉴权 | `Authorization: Bearer <访问令牌>` |
| 身份上下文 | 从令牌解析身份、身份类型与所属组织；**服务端不信任请求体中的身份字段** |
| 时间格式 | ISO 8601 带时区，写库转 UTC |
| 分页 | 入参页码与每页条数（默认 20，上限 200），返回总数、页码、每页条数与列表 |
| 幂等 | 创建类接口支持幂等键，重复提交返回首次结果 |
| 文档 | 自动生成开放接口文档，生产环境需鉴权访问 |

### 4.2 统一响应体

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "traceId": "b7f2c1e0-8f4a-4c1e-9d3a-2f6b8c0d1e2f"
}
```

**状态码语义与常规做法不同，需要特别说明**：**可预期的业务错误同样返回 HTTP 200**，具体语义由响应体中的 `code` 表达；只有参数错误、未认证、无权限、系统异常分别使用 400、401、403、500。这样客户端只需要一套统一的解包逻辑，业务分支全部集中在 `code` 上。

`traceId` 由链路追踪过滤器为每个请求生成，同时写入响应体与日志，用于问题定位。

### 4.3 错误码分段

**表 13　错误码分段**

| 段 | 含义 | 典型错误码 |
| --- | --- | --- |
| `0` | 成功 | `0` |
| `1xxxx` | 通用与参数校验 | 参数缺失、格式错误 |
| `2xxxx` | 认证与鉴权 | 未登录、令牌过期、无权限、身份不可用、验证码过频、验证码错误、刷新令牌无效、账号停用 |
| `3xxxx` | 个人日历 / 日程 / 待办 | 日程时间非法、重复规则非法 |
| `4xxxx` | 组织 / 部门 / 成员 | 部门层级超限、成员已存在 |
| `5xxxx` | 组织日历与下发 | 下发目标为空、已有接收不允许撤回 |
| `6xxxx` | 后台管理 | 管理员登录失败、需要双因素 |
| `9xxxx` | 系统 | 内部错误、第三方服务不可用 |

分段式错误码的价值在于：客户端可以按段做兜底处理（例如 `2xxxx` 统一跳登录），又能在段内做精确分支。

### 4.5 接口契约

接口契约是一份机器可校验的清单文件，与接口文档、实际行为三者由自动化测试绑定：

1. 生成的接口文档必须覆盖契约中的每个方法与路径，且鉴权声明与实际一致；
2. **实际发起一次不带令牌的请求**，验证受保护接口确实返回未认证、公开接口确实不返回未认证。

第二点是行为验证而非文档验证——接口注解写错同样会导致构建失败。

## 5. 后端关键实现

### 5.1 认证与会话

**表 15　令牌设计**

| 令牌 | 有效期 | 存储 | 说明 |
| --- | --- | --- | --- |
| 访问令牌 | 2 小时 | 客户端持有 | JWT，携带身份上下文，接口层无需查库即可解析 |
| 刷新令牌 | 90 天，滑动续期 | 服务端索引 + 客户端持有 | 每次刷新换发新令牌 |
| 注册 / 选择身份令牌 | 30 分钟 | 客户端临时持有 | 仅用于首次建号与选定身份 |

**两个实现要点：**

1. **刷新令牌轮换 + 并发宽限期**。每次刷新都换发新的刷新令牌，同时旧令牌在 60 秒宽限期内仍被受理——移动端并发发起多个刷新请求时（例如同时刷新列表与推送注册），落在宽限期内的请求会返回**同一个新令牌**，而不是判定失效把用户踢出。这是「莫名其妙要求重新登录」最常见的成因，已用测试锁定。
2. **服务端维护刷新令牌索引**。刷新令牌本身无状态，但服务端记录其归属的设备与身份，因此可以实现「查看活跃设备」「踢出指定设备」「封禁账号后全量吊销」这些 JWT 本身做不到的能力。

### 5.2 权限模型

权限判定统一遵循「**范围前缀匹配**」：

```
可管理范围 = 被授权部门的物化路径前缀
组织管理员 / 拥有者 = 全组织（不受部门限制）
```

判定入口统一在服务层，越权一律返回无权限错误码。几个关键规则：

- 组织日程对成员只读，写接口按权限矩阵直接拒绝；
- 管理员只能访问所属组织的数据；
- 组织处于停用状态时，其成员访问组织接口一律拒绝；
- 封禁账号或停用身份时，同步吊销该账号全部刷新令牌。

### 5.3 重复日程

重复日程使用标准 RRULE 表达，由 lib-recur 展开。三个容易出错的点都已在实现中处理并有测试锁定：

**表 16　重复日程的实现要点**

| 要点 | 处理方式 |
| --- | --- |
| 展开时区 | 必须按**事件自身时区**展开。「每周一 09:00（东八区）」要落在当地周一上午，而不是 UTC 周一 |
| 编辑范围 | 支持「全部 / 仅本次 / 本次及以后」三种；「仅本次」写入例外表，「本次及以后」把原序列截断并从本次克隆新序列 |
| 截断精度 | 数据库时间戳为微秒精度，截断时退让量必须大于该精度。实现中退让 **1 毫秒**——退让 1 纳秒会被数据库四舍五入回原时刻，导致整条序列未被截断 |

已知限制：若原重复规则使用「次数」表达结束条件，拆分后新序列会重新计数，因此推荐使用「截止时间」表达。

### 5.4 提醒与日程待办互转

- **提醒采用整体覆盖语义**：写入某目标的提醒时，先清空该目标的全部提醒再写入新集合。客户端因此不必自行计算增删差异，传空集合即清空；服务端负责校验提醒只能挂在自己有权访问的日程或待办上。
- **日程与待办互转采用「新建目标 + 来源标记取消」**，而不是原地修改类型。原地改类型会让挂在来源上的提醒等关联失效，重建则保证所有关联关系的语义始终一致。待办转日程时，若未提供时间则回退到待办的截止时间。

### 5.5 组织日程下发

下发时按范围**快照展开**为成员级的接收记录：管理员选定下发范围后，服务端在下发当刻就把「这条日程发给了谁」展开成一条条成员级记录，而不是在下发规则上做动态计算。这样成员端查询「发给我的日程」是一次简单查询，投递对象也全程可追溯。实现上的要点：

- 展开依赖部门物化路径，一次前缀匹配取出目标成员集合；
- 接收记录含出现日期维度，为将来支持重复日程留出结构；
- 编辑组织日程时可选「补投」新成员，否则新入组成员不补收历史日程（有测试锁定该行为）。

**表 17　批量导入实现**

| 环节 | 实现 |
| --- | --- |
| 文件解析 | 支持 `.xlsx` 与 `.csv`；使用 Apache POI 与 commons-csv |
| 数字还原 | 手机号被表格软件按数字存储时会变成科学计数法，读取时按整数还原 |

### 5.7 智能助手：工具循环与写操作授权

助手采用「模型 + 服务端工具循环」的实现结构：

```
用户消息 → 模型（流式）
    ├─ 模型调用只读工具 → 服务端直接执行 → 结果回填 → 继续
    └─ 模型调用写工具   → 服务端产出授权请求 → 阻塞等待用户答复
                              ├─ 允许 → 调用既有业务服务写入 → 结果回填 → 继续
                              └─ 拒绝 → 回填「用户已拒绝」 → 继续
                                     ↓
                              模型不再调用工具 → 结束本轮
```

**表 18　助手实现要点**

| 要点 | 实现 |
| --- | --- |
| 工具集 | 五个，全部只作用于当前用户个人日程：列表查询、分段读取备注、创建、修改、删除 |
| 写权限 | 模型不直接持有；写工具只产出授权请求，由服务端阻塞等待用户答复（上限 90 秒）后执行 |
| 消息配对 | 对话历史中「工具调用」与「工具结果」严格成对；客户端回放与服务端发送前各修正一遍（缺结果补中断标记、孤立结果丢弃） |
| 流式输出 | 服务端以流式事件推送文本增量、工具调用与授权请求，客户端边收边渲染 |
| 隐私 | 对话不落库，仅存在于客户端本次运行内存；语音转写后音频立即丢弃 |
| 降级 | 未配置模型密钥时接口明确返回「未接入」，客户端据此提示，而非写死的开关 |

### 5.8 图像文本解析

图像识别在手机本地完成，仅上传识别文字。后端负责把**一段无序的识别文本**解析为结构化的日程草稿列表：识别日期、时间、标题、地点等要素，输出草稿与逐条的原文片段，交由客户端确认页展示。

这样拆分的好处是：后端解析逻辑可以脱离图像输入进行测试（直接以文本为输入），并与「识别」这一外部环节解耦。

### 5.9 节假日数据管理

节假日数据不写在代码里，而是落在数据表中，服务端只负责读取与缓存：

- **自动同步**：每天定时拉取当年与次年数据，幂等写入（按「国家 + 日期」唯一约束做更新），同步成功后主动清除缓存；
- **离线导入**：提供脚本从本地数据文件导入，供无外网环境或需要立即生效时使用；
- **失败可见**：同步状态（最近运行时间、最近成功时间、错误信息）通过服务信息接口暴露——后台任务最糟糕的失败方式是静默失败，库里还是去年的安排而界面上看不出来；
- **缺数据时的行为**：某年无数据时返回空列表，界面不显示休班标记，不猜测、不硬编码兜底。

只记录「与常规周末不同的日子」：普通周末由客户端按星期判断，调休上班日单独记录。

### 5.10 文件上传与第三方代理

- **图片上传**：按**文件头字节**判定真实格式，不信任客户端声明的类型；限制单文件大小；文件名取内容哈希实现天然去重；对外返回相对路径，换域名或接 CDN 都无需改数据。
- **地图服务**：客户端只调用本服务的地图接口，由服务端代理第三方地图服务，密钥不离开服务端；定义统一的服务商接口，未配置密钥时降级为内置的本地实现，保证开发与自动化测试可离线运行；降级状态通过服务信息接口对客户端可见。

```
app/src/
├── App.tsx          应用根组件与导航栈
├── api/             接口客户端（统一错误处理、令牌刷新重放、各域调用、契约类型）
├── auth/            会话管理、令牌存储、组织账号记录、同意状态
```

两条结构性约定：

1. **纯逻辑与原生能力分离**。日历展开、重复规则、提醒计算、时间展示、表单校验、草稿转换等全部放在不依赖原生模块的纯逻辑层，可在 Node 环境直接运行单元测试；一旦纯逻辑文件引入原生模块，测试环境会因缺少原生运行时直接失败。
2. **原生能力通过接口注入**。识别流水线把「读取图像像素」与「模型推理」抽象为接口，测试时用模拟实现端到端跑通，覆盖坐标偏移、顺序错乱、置信度偏低等异常场景。

### 6.3 App 的会话与请求链路

**表 25　App 会话关键机制**

| 机制 | 实现 |
| --- | --- |
| 令牌存储 | 访问令牌与刷新令牌存入系统安全存储，普通存储只放非敏感缓存 |
| 提前刷新 | 计算令牌剩余有效期，不足阈值时先刷新再发业务请求，避免临界过期 |
| 并发刷新合并 | 同一时刻只允许一个刷新请求在途，其余调用共享同一个结果，避免并发刷新导致令牌轮换互相覆盖 |
| 失败重放 | 业务请求遇到未认证时，强制刷新一次并重放原请求，且仅重放一次，防止死循环 |
| 多组织账号 | 每个已认领的组织账号各自持有一份令牌，进入组织视图时按其令牌发起请求 |
| 请求头兼容 | 显式声明 JSON 内容类型——移动端网络实现对字符串请求体默认使用二进制类型，会被服务端以不支持的媒体类型拒绝 |

会话层与服务端设计形成两层保障：客户端合并并发刷新，服务端为令牌轮换设并发宽限期（见 §5.1）。

| App | 纯逻辑单测 + 全量类型检查 | 时间与重复规则、提醒计算、会话刷新、表单判定、识别流水线、更新判定 |
| Web | 组件与交互单测 | 路由守卫、未认证跳转、接口地址解析、表格与表单交互 |

前端测试与后端测试在持续集成中并行执行（见 §9.3）。

## 7. 安全实现

**表 19　安全措施**

| 面向 | 措施 |
| --- | --- |
| 密码 | 单向哈希存储（BCrypt，强度不低于 cost 10） |
| 验证码 | 短时效存储、发送频控、一次性校验 |
| 身份证号 | AES-GCM 加密存储，另存指纹用于唯一性判定，明文不落库 |
| 越权 | 服务层强制校验所有权 / 组织归属 / 部门范围 |
| 会话 | 刷新令牌可吊销；封禁账号即时失效全部会话；支持踢出单设备 |
| 登录防护 | 后台连续失败锁定；登录日志记录失败原因、IP 与客户端信息 |
| 日志 | 敏感字段不入日志；手机号、邮箱默认脱敏展示 |
| 审计 | 审计与登录日志仅追加，不可修改删除 |
| 上传 | 按文件头校验类型、限制大小，防止伪装扩展名 |
| 导入 | 限定文件类型与大小，单元格按文本解析，防公式注入 |
| 配置 | 密钥与连接信息全部经环境变量注入，禁止硬编码 |
| 上线自检 | 启动时检查危险配置（如验证码回显）是否被误带入生产环境，命中即拒绝启动 |

## 8. 部署与运行

### 8.1 组件与端口

**表 20　运行组件**

| 组件 | 作用 | 暴露方式 |
| --- | --- | --- |
| 反向代理 | HTTPS 终止、静态资源托管、接口转发、下载分发 | 对外唯一入口 |
| 后端服务 | Spring Boot 应用（单一可执行包） | 仅内网 |
| 数据库 | PostgreSQL | 仅内网 |
| 缓存 | Redis | 仅内网 |

所有组件以容器方式编排，数据卷持久化，对外只暴露反向代理端口，应用与数据库不直接对外。

### 8.2 配置注入

数据库连接、缓存连接、短信与推送密钥、地图与邮件凭据、模型密钥等全部通过环境变量注入，区分开发、预发、生产三套配置。应用包本身不含任何环境专属信息，同一个包可在任意环境部署。

### 8.3 发布与升级

**表 21　发布流程**

| 步骤 | 操作 |
| --- | --- |
| 1 | 本地构建可执行包（跳过测试的快速构建或完整构建） |
| 2 | 上传应用包至服务器部署目录 |
| 3 | 重建并重启后端容器 |
| 4 | 验证：公开接口返回正常，受保护接口返回未认证（未认证说明路由存在且鉴权生效） |

需要说明的是：Spring Boot 启动阶段存在约 **30–45 秒**的服务窗口，此期间的请求会返回网关错误，属正常现象，等待启动完成即可。

数据库迁移随应用启动自动执行，因此发布流程中不需要独立的数据库操作步骤。

### 9.2 测试

**表 22　测试层级**

| 层级 | 工具 / 方式 | 覆盖内容 |
| --- | --- | --- |
| 后端集成测试 | 嵌入式 PostgreSQL + 嵌入式 Redis | 真实执行全部数据库迁移，跑通认证、日程、组织、后台等完整业务链路 |
| 接口契约测试 | 应用上下文内的行为验证 | 文档覆盖 + 未授权请求行为，作为构建门禁 |
| 客户端逻辑测试 | 纯逻辑单元测试 + 类型检查 | 时间与重复规则、提醒计算、表单判定、识别流水线 |

后端测试使用**嵌入式数据库与嵌入式缓存**，不需要启动任何容器即可运行完整集成测试，这使得持续集成环境可以保持极简，也让开发者本地一键复现。

### 9.3 持续集成

持续集成配置两个任务：后端任务执行完整构建与测试（含契约门禁）；前端任务依次执行依赖安装、设计令牌构建、管理后台构建、App 类型检查与全部单元测试。任一环节失败即阻止合入。

## 10. 性能与容量

**表 23　性能设计**

| 项 | 设计 |
| --- | --- |
| 接口响应 | 常规接口设计目标为 P95 不超过 300 毫秒（不计第三方调用） |
| 日历查询 | 支持单日历万级日程的月份视图加载；重复规则先按范围粗筛、再在应用层展开 |
| 列表接口 | 强制分页，避免一次性返回全量数据 |
| 批量导入 | 单批不超过 5000 行，异步执行并可查询进度，避免长请求占用连接 |
| 后台导出 | 走异步任务，避免长连接阻塞 |
| 缓存 | 节假日、部门树等低频变更数据使用缓存并设置失效策略 |
| 连接池 | 数据库与缓存连接池按实例规格配置，避免连接耗尽 |
